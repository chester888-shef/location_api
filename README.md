# Мапа популярності локацій

Готовий MVP за специфікацією v2.0: етапи 1–6 та погоджений Swagger.
Session/CSRF, користувачі, категорії, локації з Soft Delete, відгуки й голоси,
перегляди, ORM-рейтинг/популярність, фільтри, пагінація, Redis-кеш та JSON/CSV.
Бонусні сповіщення й підписки не реалізовані.

## Локальний запуск

Потрібні Docker із Compose v2, інтернет для образів/залежностей/Swagger
та вільний порт 8000. Усі команди виконуй із кореня проєкту, де лежить `compose.yaml`.

1. Лише для першого запуску скопіюй налаштування:

   ```bash
   cp .env.example .env
   ```

   У `.env` заміни `SECRET_KEY` та `POSTGRES_PASSWORD` власними значеннями.
   Наявний `.env` збережи без перезапису.
2. Запусти або онови сервер:

   ```bash
   docker compose up --build -d
   ```

3. Дочекайся завершення міграцій і повідомлення Gunicorn `Booting worker`:

   ```bash
   docker compose logs -f web
   ```

   `Ctrl+C` закриває лише перегляд логів, сервер продовжує працювати.
4. Відкрий [Swagger](http://localhost:8000/api/docs/); `/` веде туди ж.
   Міграції виконуються автоматично.

Адміністратор для перевірки прав:

```bash
docker compose exec web python manage.py createsuperuser
```

## Перевірка через Swagger

Використовуй **Try it out → Execute**. Swagger передає session cookie й актуальний CSRF.

1. `GET /api/auth/csrf/` → **200**.
2. `POST /api/auth/register/` з email/password → **201**; дубль email → **400**.
3. `POST /api/auth/login/` → **200**, `POST /api/auth/logout/` → **204**.
4. Після входу створи категорію (`{"name":"Парки"}`), потім локацію за прикладом
   Swagger, підставивши ID категорії → **201**.
5. Створи другий акаунт для перевірки чужих об’єктів, відгуків та голосів.

## Права, відгуки та перегляди

- Гість читає списки, деталі й експорт; створює лише авторизований користувач.
- Категорії змінює/видаляє лише superuser; іншим **403**. Видалення залишає
  локацію з `category=null`; наступна її зміна вимагає нової категорії.
- Локацію змінює/видаляє автор або superuser; чужі зміни → **403**.
  POST/PUT вимагають шести полів із прикладу Swagger; невалідні дані → **400**.
- DELETE локації → **204**. Звичайний користувач більше її не бачить (**404**),
  superuser може лише читати її та відгуки. Пов’язані зміни заборонені.
- `POST /api/locations/{id}/reviews/` з `{"rating":4,"comment":"Гарне місце."}`
  → **201**; повтор від того самого автора → **409**, невалідний рейтинг/коментар → **400**.
- Автор відгуку або superuser: `PATCH /api/reviews/{id}/` → **200**, DELETE → **204**.
  Відгук видаляється фізично разом із голосами.
- Інший акаунт: `PUT /api/reviews/{id}/vote/` із `{"value":"like"}` → **200**;
  зміна на `dislike` оновлює той самий голос. DELETE → **204**, повтор теж **204**.
  Голос за власний відгук → **403**, включно із superuser.
- GET деталей активної локації додає перегляд не частіше одного разу за 3600 секунд.
  Для користувача ліміт спільний між сесіями; для гостя — за session cookie.
  Списки, експорт, HEAD/OPTIONS і видалені локації переглядів не додають.
- Два відгуки з оцінками 1 та 5 дають `rating=3`, `reviews_count=2`.
  Без відгуків `rating=null`. Рейтинг округлюється для відображення до 2 знаків.
  `popularity = 0.5 × rating + 0.3 × ln(1 + reviews_count) + 0.2 × ln(1 + views_7d)`;
  порожній рейтинг у формулі — 0, `views_7d` охоплює останні 7 діб.

## Етап 6: списки, кеш та експорт

1. GET списків локацій, категорій і відгуків повертає
   `count/next/previous/results`, по **10 записів**. Перевір `page=2` на списку
   з понад 10 записами та переходи `next/previous`. Невалідна сторінка → **400**.
2. Для `/api/locations/` доступні `search` (назва/опис), `category`, `author`,
   `rating_min/rating_max` (1–5), `ordering`: `created_at`, `rating`, `popularity`
   або ті самі з `-`. Невідоме сортування чи min > max → **400**.
   Порожній рейтинг іде в кінець сортування й не проходить фільтри рейтингу.
   Межі порівнюються з точним середнім: оцінки 4, 5, 5 дають у відповіді `4.67`,
   проходять `rating_min=4.66`, але не проходять `rating_min=4.67`.
3. Список кешується на **300 секунд**, окремо для фільтрів/сортування/сторінки.
   Superuser обходить кеш. Для ручної перевірки відкрий список із `search=Тест`,
   створи локацію з цією назвою й повтори запит: вона має з’явитися одразу.
   Зміни/видалення локацій, відгуків і категорій також змінюють ревізію кешу.
   Перегляди й голоси її не змінюють: статистика списку може відставати до 5 хвилин,
   деталі й експорт повертають свіжі значення.
4. GET `/api/locations/export/json/` повертає масив, `/api/locations/export/csv/`
   — CSV для завантаження. Права, фільтри та сортування ті самі, що у списку;
   експорт містить **усі** відповідні записи, без пагінації та кешу.
   Поля відповідають локації зі статистикою, крім `is_deleted`.
5. CSV має UTF-8 BOM, кирилицю та захист текстових формул апострофом.
   Від’ємні координати залишаються числами. Формування одним pandas DataFrame
   у пам’яті — обмеження MVP для невеликих наборів даних.

Приклади без авторизації (superuser може додатково бачити видалені записи через Swagger):

```bash
curl 'http://localhost:8000/api/locations/?ordering=-popularity&page=1'
curl 'http://localhost:8000/api/locations/export/json/?search=парк&ordering=-rating'
curl -H 'Accept: text/csv' 'http://localhost:8000/api/locations/export/csv/?ordering=-popularity' -o locations.csv
```

Для перевірки збою Redis виконай `docker compose stop redis`, потім повтори GET
списку й деталей: відповіді працюють, перегляди в межах години не дублюються.
Поверни Redis командою `docker compose start redis`. PostgreSQL зберігає ліміт та історію.

## Виправлення після рев’ю

- Дробові `category` ID та `true/false` у координатах → **400** для POST/PUT/PATCH.
  Перевір PATCH із `{"latitude":true}` або ID наявної категорії + `0.5`.
- Якщо видалення локації/категорії завершилося перед конкурентним оновленням,
  оновлення → **404**, без відновлення об’єкта. Втрачена категорія локації → **400**
  у полі `category`. Якщо запис уже заблокував категорію, її видалення чекає commit.
- Регресії перевіряють окремі з’єднання PostgreSQL, дані й ревізію після відмови.
  Поля JSON/CSV у контрактному тесті задані незалежно від серіалізатора.
- Запис локацій і категорій, блокування та інвалідація виконуються в сервісах.
  Rollback перевіряється після реального збільшення ревізії. Фікстура готує її
  для тестів із БД; окремий тест міграції починає з порожньої таблиці.
- Формулу перевіряють unit-тест ORM-виразу без БД і числові тести PostgreSQL.

```bash
docker compose build web
docker compose run --rm web pytest tests/test_write_services.py tests/test_location_concurrency.py tests/test_cache_revision.py tests/test_popularity_expression.py tests/test_popularity.py tests/test_export.py -q
```

## Скидання пароля

`POST /api/auth/password-reset/` з email → **200** з нейтральною відповіддю.
Локальний лист знайди через `docker compose logs --tail 80 web`.
Передай `uid`, `token`, `new_password` у `/api/auth/password-reset/confirm/` → **200**;
повтор токена й вхід зі старим паролем → **400**. Новий пароль дозволяє увійти.
Клієнтської сторінки за посиланням із листа в MVP немає.
Строга одноразовість токена за конкурентних confirm-запитів не гарантується.

## Автоматичні перевірки

Після зміни коду перебудуй образ. Перевірки етапу 6:

```bash
docker compose build web
docker compose run --rm web pytest tests/test_list_cache.py tests/test_export.py tests/test_docs.py -q
```

Повна перевірка:

```bash
docker compose run --rm web pytest -q
docker compose run --rm web python manage.py check
docker compose run --rm web python manage.py makemigrations --check --dry-run
docker compose run --rm web python manage.py spectacular --validate --fail-on-warn --file /tmp/openapi.yaml
```

Очікуються `passed`, код 0, відсутність нових міграцій і попереджень OpenAPI.
Холодний запуск тестів: `docker compose down`, потім команда `pytest` вище.
Тести використовують окрему PostgreSQL-базу `test_...` та Redis DB 1; робочі дані
не очищаються, реальні листи не надсилаються. Зупинка — `docker compose down` без `-v`.

## Налаштування

Локально пошта виводиться в логи; для SMTP задай `EMAIL_BACKEND` та `EMAIL_*`.
`EMAIL_TIMEOUT=5`, гарантії доставки немає. Reset-токен діє до 3 діб та стає
недійсним після зміни пароля. Секрети `.env` не додавай до системи контролю версій.
Змінні shell мають пріоритет над `.env`; `DEBUG` приймає `true/false` або `1/0`.
Для HTTPS: `DEBUG=false`, відповідні `ALLOWED_HOSTS`, `SESSION_COOKIE_SECURE=true`,
`CSRF_COOKIE_SECURE=true`.
